不是跑 E2E 套件，而是**扮演一个没读过文档的玩家**，只用 `--help` 和 README，

## P0-1 · 版本 ID 一进 `requiredJavaMajor` 就返回 21，26.x 全部起不来

**现象**：装完 26.2 整合包（部署后检查 OK），启动直接死在 JVM：

```
$ blockpilot run fabric-loader-0.19.5-26.2 --root .tmp-user/mc --instance fo --offline
Unrecognized option: --sun-misc-unsafe-memory-access=allow
Error: Could not create the Java Virtual Machine.
  异常退出  code=1 · 0.0s
```

**根因**（两处叠加，任一处都足以致命）：

`src/core/java/select.ts:71` 传进去的是**版本 ID**，不是游戏版本：

```ts
const needMajor = opts.versionId === undefined ? undefined : requiredJavaMajor(opts.versionId)
// versionId = "fabric-loader-0.19.5-26.2"
```

`src/core/java/types.ts:25-30` 的正则匹配不到 `fabric` 开头，落兜底：

```ts
const m = /^(\d+)(?:\.(\d+))?(?:\.(\d+))?/.exec(gameVersion)
if (!m) return 21
...
if (major !== 1) return 21      // 26.2 也走这里
```

实测返回值：

```
 21  <-  26.2                        真实需求：25
 21  <-  fabric-loader-0.19.5-26.2
 21  <-  fabric-loader-0.19.3-1.21.1   （碰巧对）
 17  <-  1.20.1                        （对）
```

**为什么之前没暴露**：1.21 恰好吃 Java 21，兜底值刚好蒙对。T3 在 1.21.1 上跑通，
掩盖了「所有带 loader 前缀的 ID 都返回 21」这个事实。

**而正确数据就在手上**：`versions/26.2/26.2.json`

```json
"javaVersion": { "component": "java-runtime-epsilon", "majorVersion": 25 }
```

`src/core/launch/index.ts:45` 确实读了它（`javaMajorVersion: version.javaVersion?.majorVersion`），
但**选 Java 发生在加载版本 JSON 之前**（`pickJavaOrReport` 先跑），拿不到。

**连带**：预检也基于同一个函数，所以 `preflight` 对「Java 21 跑 26.2」判 OK（见 P0-3）。
一个错误函数污染了选 Java、预检、报错三处。

**修法方向**：`requiredJavaMajor` 只接受 gameVersion 时才有意义——先 `resolveVersion` 拿到 JSON，
读 `javaVersion.majorVersion`；读不到再退回映射表，并在映射表里补 26.x。
顺带补一条「版本 ID 带 loader 前缀」的用例。

## P0-2 · 一次成功的启动，被 diag 判成「崩在 Controlify」

**现象**：`run --stop 25` 正常启动（模组全加载、LWJGL 就位、按时限干净退出，309 行日志），
回头 `diag` 这份日志：

```
最可能的根因
  ✗ mixin  第 192 行
    InvalidMixinException: Found a remappable @Shadow annotation on method_2659 ...
    → 模组之间的字节码改写冲突 ... 本次崩在 Controlify

指向的模组（按证据强度排序）
  ✗ controlify · Controlify 3.0.0+lts+1.21.1-fabric · 3 个栈帧
```

**反证**：整份日志只有 1 条 ERROR（第 192 行），之后还有 **117 行正常运行**，
末尾停在 `Backend library: LWJGL version 3.3.3-snapshot`，退出码 0。

**根因**：`src/core/diagnostics/crash.ts:90` 把 `InvalidMixinException` 一律标成 `fatal`：

```ts
{
  re: /MixinApplyError|InvalidMixinException|InvalidInjectionException|Mixin apply failed|MixinTransformerError|Mixin transformation of .* failed/i,
  kind: 'mixin',
  severity: 'fatal',
  ...
}
```

只匹配异常文本不够。同一个 `InvalidMixinException` 有两种结局：真的把游戏拦死在启动阶段，
或者 Loader 把那个 mixin 禁掉继续跑。区别不在异常本身，而在**它之后日志有没有走到下一个
里程碑**。现在的判定只看"出现了什么异常"，于是后者被报成崩溃。

同一个文件里其实已经有了这个思路——`ModLoadingException` 被刻意标成 `warning`，注释写
「这是结果不是原因」。缺的只是"之后进程还活着吗"这个证据。

<!-- 更正：本条初稿写成「core 判得对，是渲染层把 inconclusive 抹平成 crash」，那是错的。
     当时用 `blockpilot ... | grep -v 代理; echo $?` 读退出码，拿到的是 grep 的退出码，
     据此反推出 verdict=inconclusive。实际 verdict=crash、severity=fatal，误判在 core 层。
     教训与被测代码同源：证据不足时不要下确定结论。 -->

**影响**：这条恰恰违背 README 的承诺——「定位不到时会直说，不会猜一个名字给你，
照着删错模组，问题还在，还多一个」。现在用户启动成功了，却被告知崩在 Controlify，
下一步就是去删它。Mixin 对个别 mixin 的兼容性告警在 MC 生态里很常见，不是崩溃。

**修法方向**：`inconclusive` 用独立措辞（「找到一条可疑记录，但游戏之后继续运行了」），
不用红叉、不用「最可能的根因」；有 `run` 的退出码时优先信退出码。

## P0-3 · 同一个包，装前 BLOCKED、装后 OK

**现象**：

```
$ blockpilot preflight Fabulously.Optimized-v14.1.1.mrpack
  verdict   BLOCKED
  ✗ VERSION_MISMATCH  MixinTrace Reborn 1.0 for 26.1 Universal 不支持 Minecraft 26.2
    → 该模组支持的版本：26.1, 26.1.1, 26.1.2
  exit 2

$ blockpilot deploy ... && blockpilot preflight <实例目录>
  装好了  26.2 + fabric 0.19.5 · 模组 51 个（失败 0）· 部署后检查 OK
  没有发现阻塞项
  verdict   OK
```

**反证**：那个被判「不支持」的模组，jar 里写的是通配范围：

```
$ unzip -p mods/mixintrace-1.0-26.1-universal.jar fabric.mod.json
depends: {"minecraft":"26.x"}
```

`26.x` 覆盖 26.2。Modrinth 网页上的 `game_versions` 列表（26.1–26.1.2）滞后于 jar 内声明。

**根因**：`src/core/preflight/check.ts:100`

```ts
if (!info.gameVersions.includes(instance.gameVersion)) {
  severity: 'blocker'      // 只凭在线声明的列表，判死
```

**这是 ADR-0025 没走完的那一步**：昨天刚因为「jar-in-jar 看不到」把缺失依赖从 blocker
降到 warning，理由是「预检只说有证据的话」。同一条理由对 `VERSION_MISMATCH` 一样成立——
在线 `game_versions` 不含目标版本，只能证明**作者没勾那个框**，不能证明跑不了。
何况项目自己装完一读 jar 就改口说 OK，等于自证前一次判断不可靠。

**影响**：FO 是下载量千万级的官方稳定包，第一次用就判「装不上」，退出码 2；
写脚本的人会直接中止。ADR-0014 那句「如果用户第一次用就撞上，他不会怀疑是启动器错了」
在这里第三次重演（第一次 JiJ、第二次 unknown、这次版本声明）。

**修法方向**：`VERSION_MISMATCH` 降 warning，与 `UNVERIFIED_DEPENDENCY` 同级；
把「装完再 preflight 实例」写进 hint。真要判死，得等能读到 jar 内的 `depends`。

## P1-1 · 未知参数一律静默忽略，`--root` 缺值会吞掉下一个 flag

**现象**：

```
$ blockpilot preflight pack.mrpack --jsno         # 拼错
（正常输出人类可读文本，退出码 0）

$ blockpilot launch <ver> --root --instance fo    # 忘了写路径
（不报「缺值」，直接去默认 %APPDATA%\BlockPilot 找，然后报「版本不存在」）

$ blockpilot launch <ver> --root --china --inst fo
（root 被设成字符串 "--china"）
```

**根因**：`src/cli/index.ts:168`

```ts
function argOf(argv, name) {
  const i = argv.indexOf(name)
  return i === -1 ? undefined : argv[i + 1]     // 不检查下一个是不是 flag
}
```

没有未知参数校验，各子命令只做 `argv.includes('--xxx')`。

**影响**：`--jsno` 拿到文本却以为是 JSON，脚本 `JSON.parse` 在别处炸；`--root` 缺值
会把 150 MB 装到用户没想到的盘。这两条都是「静默做错事」，比报错难查得多。

**修法方向**：为每个子命令声明允许的 flag 白名单，未识别即 `usage()` + 退出码 1；
`argOf` 遇到下一个 token 以 `--` 开头时视为缺值。

## P1-2 · `verdict=unknown` 退出码 0（复审后：这是有意的契约，不改）

**现象**：所有模组都拿不到元数据（等于什么都没验），仍然 exit 0：

```
$ blockpilot preflight all-unresolved.mrpack
  verdict   UNKNOWN
  mods      2  (resolved 0, unresolved 2)
  i UNRESOLVED_MOD ... ×2
  exit 0
```

**复审**：我一度把这条改成退出码 3，结果 `E2E-004` 立刻红了。那条用例的标题就是
「unknown 不能当违规」，断言 `exit 0`——项目早就定过这个契约：`unknown` 是「没证据」，
不是「有问题」，用非零码会让离线场景（拿不到元数据）下正常实例全都报错。

**结论**：不动退出码。真正缺的是文档——README 没写「unknown 也是 0，要区分请读
`--json` 的 verdict 字段」。使用者只能靠猜。

## P1-3 · `--china` 的元数据只走镜像，失败不回退

**现象**：走代理环境下 `--china` 直接失败，而同一台机器上直连镜像其实是好的：

```
$ blockpilot launch ... --china
网络错误：无法访问 https://bmclapi2.bangbang93.com/...：返回的不是 JSON
检查网络；国内可加 --china 走镜像        ← 我就是加了 --china 才失败的
```

同一条命令去掉 `--china` 正常。`fetch` 直连 BMCLAPI 是 200 / 278 KB 合法 JSON。

**根因**：`src/core/version/fetch.ts:19` 二选一：

```ts
return getJson(opts.mirror === true ? BMCLAPI_MANIFEST : MOJANG_MANIFEST, opts.signal)
```

而下载那边 `chinaFirstSources()` 是 `[bmclapi, neoforgeCdn, mcim, direct]`，**有直连兜底**。
同一次部署里就能看到下载自动切源（`↓ xxx.jar  direct`），元数据却不会。

**影响**：README 把 `--china` 作为国内标准路径推荐。镜像一挂、或用户网络对 302 链不友好，
整条路就断，且错误提示还在劝用户「加 `--china`」。

**修法方向**：元数据也按源列表顺序重试，第一个成功即用；失败时把每个源的失败原因都打出来。

`preflight --json` 结构完整（`verdict/findings/stats/plan/generatedAt`），
`diag --json` 被静默忽略，只吐人类可读文本。而 MCP 的 `diagnose_crash`

## P2-2 · 依赖解析不区分加载器，报出来的是裸 project id

```
! UNVERIFIED_DEPENDENCY  w7ThoJFB 需要前置模组 1vrSzlao，元数据里没有兼容版本
需要人工处理
  ? 1vrSzlao  找不到兼容当前游戏版本与加载器的版本
```

`1vrSzlao` = KotlinLangForge，loaders 只有 `forge, neoforge`。而这是个 **fabric** 包。

同时：明明已经联网拿到了 `MixinTrace Reborn` 这样的可读名字，这条却只给 ID，
用户无法自行处理。

## P2-3 · `launch` 打印的命令不能直接复制粘贴

参数数组里有一项自带空格（Fabric profile 的原始写法）：

## P3-1 · `deploy` 不理 `preflight` 的结论

对已经判 BLOCKED 的包，`deploy` 不提示一句就开始下 150 MB。
可能是刻意分层（deploy 不替用户决策），但至少该在日志里带一句「该包预检为 BLOCKED」。

## P3-2 · README 对 `plan.installs` 的描述会误导

> `preflight --json` 里的 `plan.installs` 与下载器字段完全对齐，照着它下载即可

实际语义是「**缺失依赖**的修复计划」（`RepairPlan`）。对普通整合包是空数组：

```
FO 14.1.1 → plan.installs: 0
closure.mrpack（缺 Sodium）→ plan.installs: 1
```

照着它下载会一个文件都下不到。字段本身（`url/fileName/size/hashes/requiredBy/confidence`）
确实对齐，问题只在「照着它下载即可」这句话。

## P3-3 · `launch` 缺文件时只是不说话

1.21.1 实例末尾有「所有依赖文件都在位」，26.2 实例缺东西时这句直接消失，
不说缺什么。用户只会觉得「好像少了点什么」。

## P3-4 · 「版本不存在」落进 `unexpected error`，没有稳定码

```
$ blockpilot launch fabric-loader-0.19.3-1.21.1 --root --instance fo
unexpected error: Error: 版本不存在：fabric-loader-0.19.3-1.21.1
```

对比 `preflight` 的 `TARGET_NOT_FOUND: 找不到目标：...`，同样是「你给的名字不存在」，
一个有计划码、一个落进顶层兜底（`src/cli/index.ts:1277`）还带 `Error: ` 前缀。
`launch`/`run`/`setup` 等接受版本 ID 的子命令都走这条路径。

## 做对的地方（也值得记）

1. **`diag` 对真崩溃准且克制**：controlify-mixin / auth-failed 两份样本都归因正确，
   401 给了可执行建议（`blockpilot login`），并明说「定位不到具体模组」。
   对无异常的 clean.log 直接说「没有在日志里找到异常」，不硬凑。
2. **`install --dry-run` 的诚实**：标 `confidence: unverified`、默认不装、
   提示加 `--include-unverified`，完全落实 ADR-0025。
3. **`run` 的进程管理**：`--stop` 到点干净结束、日志按会话落盘、
   保留 10 份且不覆盖游戏自己的 `latest.log`。
4. **部署链路真实可用**：51 个模组 + 57 个 overrides 全下，失败 0；
   下载源自动 fallback（日志可见 `↓ ... direct`）；26.2 这种新版本号也能正确解析
   （`32.json` / `26.2.jar` 都对）。
5. **MCP 边界**：只开两个只读工具，`structuredContent` 齐全，smoke 通过。

## 一句话

**1.21.1 这条路走通了，26.2 这条路断在一个 Java 版本猜测上，而预检和诊断都在替这个错误背书。**

三个 P0 有同一个形状：**手上的证据不足以支撑这么确定的结论，但输出得很确定**
（猜的 Java 21、不是 crash 的 crash、滞后元数据的 BLOCKED）。
项目最值钱的东西就是「不确定时直说」，这三处都在往反方向走。

## 第二轮：换四个角色再测（同日）

上一轮是「没读文档的玩家」。这一轮换四种用法，专挑会真的踩到的姿势。

| 角色 | 关注什么 | 结果 |
|---|---|---|
| 整合包作者 | 做包时写错清单 | 6 个畸形包里 4 个报 JS 内部错，1 个穿越被放过 |
| 手滑用户 | 实例名写错 / 空 | `--instance ""` 让 gameDir 变成 `instances/` 本身 |
| 安全视角 | 恶意包能不能写出实例外 | `files[].path` 无校验，能 |
| CI 脚本 | 重跑幂等 | 幂等本身 OK；慢网络下 fabric meta 超时 |
| MCP 客户端 | 坏参数 | 干净，和 core 共用同一套校验 |

### R1（安全）包内 `path` 能穿越出实例目录

`buildPackTasks` 用它拼落盘路径，**没有任何校验**：

```ts
destPath: join(layout.gameDir, ...file.path.split('/')),
```

`path: "../../evil.jar"` 就会写到实例外面两层。同一个文件里的 `extractOverrides`
一直有 `if (name.includes('..')) continue`——两套标准，files 这边漏了。

**已修**：`readMrpackIndex` 里逐条校验 `files[].path`：不许绝对路径、不许盘符、
不许 `..` 段（反斜杠也当分隔符）。preflight 与 deploy 共用这个入口，两边同时收口。

### R2 `--instance` 不做校验

```
instance="../escaped"    → gameDir=...\iso\escaped          （逃出 instances/）
instance="../../escaped" → gameDir=...\.tmp-user\escaped    （逃出整个 root）
instance=""              → gameDir=...\iso\instances        （是目录本身！）
```

空串最要命：`--instance $NAME` 而变量没设值时，overrides 会盖进 `instances/`，
影响所有实例。

**已修**：`resolveLayout` 加 `assertInstanceId`，空串 / `.` / `..` / 含分隔符 / 盘符 /
Windows 非法字符一律抛 `LayoutError`。

### R3 清单缺字段报的是 JS 内部错误

| 包的问题 | 修之前 |
|---|---|
| 缺 `dependencies` | `TypeError: Cannot use 'in' operator to search for 'fabric-loader' in undefined` |
| 缺 `files` | `TypeError: Cannot read properties of undefined (reading 'filter')` |
| 缺 `downloads` | `TypeError: Cannot read properties of undefined (reading '0')` |
| 清单不是 JSON | `SyntaxError: Expected property name or '}' in JSON at position 2` |

写包的人看到这些，不知道自己少写了什么。

**已修**：`assertMrpackIndex` 逐字段校验，报的是「清单缺少 dependencies 对象」
「files[0]（mods/a.jar）缺少 downloads 数组」「modrinth.index.json 不是合法 JSON」。

### R4 `formatVersion: 99` 被静默接受

未来格式的包判 `OK`（0 个模组），等于给了一个假结论。

**已修**：不是 1 就抛「不支持的清单格式版本 99（本程序只认 1）」。

### R5 「版本不存在」落进 unexpected error

```
$ blockpilot launch v --root ...
unexpected error: Error: 版本不存在：v
```

**已修**：新增 `VersionNotFoundError`，CLI 映射成稳定码 ——
`VERSION_NOT_FOUND: 版本不存在：v` + `先装一次：blockpilot deploy <整合包> 或 setup <mc 版本>`。

### R6（观察，不是缺陷）重复部署的幂等性

同一包同一实例连跑：第一次 0 下载全跳过；第二三次要重走 90 个文件、卡在
`meta.fabricmc.net` 10 秒连接超时后失败。

排查后**不是幂等性问题**：90 个文件全是 cached（第三次总耗时 16 s，其中 10 s 是超时等待），
真凶是这条线路到 `meta.fabricmc.net` 要 20 s，而 undici 的连接超时默认 10 s
（`fetchJson` 的 AbortSignal 是 20 s，但连接阶段更早就断了）。

加 `--china` 后 **2.2 秒**完成，退出码 0——镜像走的是 `/fabric-meta`，这条路径本来就通。

结论：不改代码。但「重跑会因为一次连接超时失败」对 CI 不友好，是否加一次重试
留作后续讨论（重试会让慢网络更慢，需要权衡）。

前两轮是我自己设想用户会怎么用。这轮先去搜玩家实际在问什么，再照着测。

来源：MC 百科《整合包的常见问题与解决方案》、找服网《整合包安装后启动器报错怎么办》、
TrueSight《整合包故障诊断与环境部署指南》等（搜索日期 2026-11-03）。

提炼出的高频行为（按出现次数）：

| 用户在做的事 | 网上给的答案 |
|---|---|
| 调内存 | 「内存不足是闪退最常见原因」，建议 4–8 GB，不超过物理内存 75% |

### S1 `--memory` 不做任何校验（已修）

用户会照教程填 8192，也会手滑填 `abc`、`-1`、`0`。以前这些值一路拼进 JVM 参数：

```
--memory 999999 → -Xmx999999M     （1 TB）
--memory -1     → -Xmx-1M
--memory abc    → -XmxNaNM
--memory 0      → -Xmx0M
```

JVM 只会回一句 `Unrecognized option: -XmxNaNM` / `Invalid maximum heap size`，
用户联想不到是自己参数写错了——而且 `run` 之后还会被引导去 `diag` 查模组。

**已修**：`parseMemoryArg` 校验正整数 + 下限 512 + 上限 65536，给稳定码：

```
BAD_MEMORY: --memory abc 要一个整数（单位 MB），收到：abc
           例：--memory 4096
```

`4096` 仍然正常产出 `-Xmx4096M`。

### S2 离线用户名不校验（已修，只提醒不拦）

```
--user 玩家                            → 原样传给游戏
--user "a b"                           → 原样传给游戏
--user verylongusernamethatexceedssixteen（32 字符） → 原样传给游戏
```

MC 的离线名只认 `[A-Za-z0-9_]`、1–16 位。中文名单机能进，但联机会被服务端拒绝或显示
乱码——网上教程专门提醒这一点，说明踩的人很多。

**已修**：不符合规则时打一行提示，**不阻断**（单人确实能玩），并且只在没有正版账号时提示
（有账号时名字来自账号，`--user` 不生效，否则是误报）。

### S3 「没有可检查的模组」和「没验成」都说成「没有发现问题」（已修）

打包时多套一层目录是很常见的作者失误（网上那条「文件夹套文件夹」就是这个）：

```
files: ["MyPack/mods/a.jar", "MyPack/mods/b.jar"]

$ blockpilot preflight nested-bad.mrpack
  verdict   OK
  mods      0  (resolved 0, unresolved 0)
  没有发现问题            ← 一个模组都没查，却说通过
```

同一个分支还盖住了另一种情况：`verdict UNKNOWN`（元数据全没取到）时也照样打印
「没有发现问题」。

**已修**：`renderHuman` 把三种情况分开：

```
mods == 0        → 没有可检查的模组
                   清单里没有 mods/ 下的文件。如果包里有模组，检查 path 是不是多套了一层目录
verdict unknown  → 这次没有验成
                   模组元数据没取到，不代表包没问题
其余              → 没有发现问题
```

### 查了但没问题的地方

- **文件损坏**：`verifyExisting` 用哈希比对，不是看大小；`no-hash` 的文件显式不算 cached。
  注释里还写了原因（MCIM 会返回 200 + 错误页）。
- **显卡/认证/Java**：`crash.ts` 的规则里已有 `GLFW error`、`auth`、`Java 版本` 几类，
  和网上那些错误码对得上。
- **杀毒误删**：表现为文件消失，`verifyExisting` 的 `missing` 会重下。

新增 e2e：`E2E-014` 覆盖 `--memory` 的四个非法值与一个合法值。T0 14 → 15 条。
