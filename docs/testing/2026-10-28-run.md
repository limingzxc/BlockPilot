## 一、JiJ 内嵌依赖被当成缺失（`jij-false-positive`）

**现象**：真实 FO 6.5.0 被判 BLOCKED。

```
$ blockpilot preflight fixtures/fo-6.5.0.mrpack --no-host
  verdict   BLOCKED
  mods      48  (resolved 47, unresolved 1)
  ✗ MISSING_DEPENDENCY  3IuO68q1 需要前置模组 codAaoxh，它不在实例中
    → 可安装 MidnightLib 1.10.0 - Fabric 1.21.1
  ✗ MISSING_DEPENDENCY  mOgUt4GM 需要前置模组 eXts2L7r，它不在实例中
    → 可安装 2.4.2+1.21
  exit 2
```

**反证**：两个「缺失」的依赖就在包内，只是打在别的 jar 里（Jar-in-Jar）：

```
puzzle-fabric-2.3.0+1.21.1.jar  → META-INF/jars/midnightlib-1.9.2+1.21.1-fabric.jar
modmenu-11.0.4.jar              → META-INF/jars/placeholder-api-2.4.0-pre.2+1.21.jar
```

真实游戏日志（`instances/fo/logs/latest.log`）里 151 个模组正常加载，证明包是完整可跑的。

**根因**：`src/core/deps/closure.ts:42`

```ts
const installed = new Set(roots.map((r) => r.projectId))
```

闭包只认顶层 Modrinth `projectId`。JiJ 里的模组只有 loader 侧的 modId（`midnightlib`），没有 Modrinth
projectId，两边对不上，于是被判缺失。

**影响**：对下载量 1900 万的主流 Fabric 包，第一次用就报「跑不了」，还给出装重复 mod 的修复计划。
ADR-0014 里那句「如果用户第一次用就撞上，他不会怀疑是启动器错了」在这里原样重演。

**修法方向**：缺失时把 Modrinth project 的 slug 取回来，与 jar 内嵌套 mod id 比对（`read.ts` 已经能读
`META-INF/jars/*`）；或者直接把嵌套 mod id 并进 `installed`。两条都要补一条真实包用例。

**回归用例**：E2E-101、E2E-102。

## 二、非严格 JSON 的 mod 被整包丢弃（`jar-lenient-json`）

**现象**：48 个真实 jar 里有 2 个读不出元数据。

```
$ blockpilot preflight fixtures/mcroot/instances/fo --no-host
  i UNREADABLE_JAR  2 个 jar 读不出模组元数据，未参与检查
    → BetterGrassify-1.8.6+fabric.1.21.1.jar、Debugify-1.21.1+1.0.jar
```

**证据**：这两份 `fabric.mod.json` 的 `description` 里有裸换行（合法 JSON 不允许），Fabric 自己用
Gson 的 lenient 模式解析，所以游戏里正常加载：

```
BetterGrassify-1.8.6+fabric.1.21.1.jar  strict JSON FAIL: Bad control character in string literal (position 161)
Debugify-1.21.1+1.0.jar                strict JSON FAIL: Bad control character in string literal (position 156)
sodium-fabric-0.6.13+mc1.21.1.jar      strict JSON ok
```

**根因**：`src/core/modmeta/read.ts:44` 直接 `JSON.parse`。

**影响**：这两个模组静默退出所有检查，崩溃时也不可能被归因。用户看到的是「检查通过」，实际少了 4%
的样本。

**修法方向**：`JSON.parse` 失败后，把字符串内的裸控制字符转义再试一次；仍失败才记 `UNREADABLE_JAR`。

**回归用例**：E2E-011。

## 三、自建实例没有版本元数据（`instance-no-version`）

**现象**：

```
$ blockpilot preflight fixtures/mcroot/instances/fo --no-host
  verdict   WARN
  ! UNKNOWN_GAME_VERSION  目录里没有版本信息，无法校验 MC 版本与 Java
```

**根因**：`src/core/instance/scan.ts:49` 只认 Prism/MultiMC 的 `mmc-pack.json`；`deploy` 装完不写任何
实例标记，所以 BlockPilot 自己的实例反而查不出游戏版本。

**影响**：README 主推的 `preflight <实例目录>` 对自己装的实例最弱——MC 版本未知，版本兼容性与 Java
检查一起失效。Prism 迁过来的实例反而更好。

**修法方向**：`deploy` 收尾写一个最小 `mmc-pack.json`（或自定义 `blockpilot.json`），`scan` 优先读。

**回归用例**：E2E-012。

## 四、启动依赖网络（`launch-needs-network`）

**现象**：所有文件都在本地，断网就出不了启动命令。

```
$ HTTPS_PROXY=http://127.0.0.1:9 blockpilot launch fabric-loader-0.19.3-1.21.1 --root fixtures/mcroot --instance fo --raw
· launch.version.fetch
unexpected error: TypeError: fetch failed
exit 1
```

**根因**：`src/core/version/resolve.ts:41` 本地没有 `versions/<id>/<id>.json` 就联网取。`setup` 只写
client jar 与 natives，**从不写这份 JSON**——`fixtures/mcroot/versions/1.21.1/` 里只有一个 jar 就是
证据。加载器版本沿 `inheritsFrom` 找父版本时必然踩到。

**影响**：装好的游戏断网不能启动；每次启动多一次无谓请求；Mojang 抖动会让「已经装好」的游戏起不来。

**修法方向**：`setup` 时把拿到的版本 JSON 落盘（`versions/<id>/<id>.json`），`resolve` 已经是本地优先。

**回归用例**：E2E-010B。

## 通过的用例说明了什么

- 离线预检的承诺成立：死代理下 `instance-miss` 仍能判 BLOCKED，`instance-ok` 保持 UNKNOWN 不升级成违规
  （ADR-0013 那条「unknown 不当违规」没有回退）。
- 真实崩溃归因仍然准：controlify 的 mixin 注入失败，`primary.kind=mixin`、第一嫌疑 `controlify`，
  3 个栈帧、三条判定依据。

  `install` 不创建 `mods/`。
- CurseForge 边界守住：说清 `CF_API_REQUIRED`，不硬判 blocked，不尝试下载。

## 第三轮：T4 与网络错误（00:00–00:15）

T4 的三个「卡点」拆开看，其实只有一个是真的：**错误信息太烂，烂到没法写断言**。

### 先修：断网被说成「模组已下架」

死代理下跑在线预检，原来的表现是：

```
i UNRESOLVED_MOD  无法获取 mods/xxx.jar 的元数据 … 内容源未返回该版本，可能已下架
× 48 条
exit 0
```

`getVersions` 的兜底逻辑是为了「一个坏 id 不该让整批失败」，但它把**网络故障**
也吞了，于是逐个重试 48 次、全部失败、全部说成「可能已下架」，最后给出 exit 0。
用户拿着这份报告查不出任何东西。

改法：

- 新增 `core/http.ts` 的 `fetchJson()`：传输失败抛 `NetworkError`，消息带**地址与底层原因**
  （`无法访问 https://api.modrinth.com/...：connect ECONNREFUSED`），查询串超长时截断；
  HTTP 非 2xx 仍是普通错误——调用方要靠状态码区分「查不到」和「连不上」。
- `ModrinthSource.getVersions`：`NetworkError` 直接向上抛，不再逐个重试。
- 预检捕获后报 `NETWORK_ERROR` + 可行动提示（`--china` / `--proxy`）；CLI 顶层也把
  `NetworkError` 单独渲染，不再是 `unexpected error: NetworkError: ...`。
