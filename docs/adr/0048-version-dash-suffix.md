# 0048. 版本号里 `-` 之后的内容：版本段还是构建号

- **Status**: Accepted
- **Date**: 2026-11-09
- **Deciders**: @liming
- **Related**: ADR-0026（版本不匹配按方向分级）、issue #14

## Context

`parseVersion` 以前把 `-` / `+` 之后的**整段**丢掉，只留主版本号：

```
compareVersions('1.20-3.1.43', '1.20-2.7.32') => 0
satisfiesRange('1.20-3.1.43', '<=1.20-2.7.32') => satisfied
```

`1.20-<modversion>` 是模组圈最常见的写法之一（`supplementaries-1.20-3.1.43`、
`SlashBlade-1.20.1-1.1.23`），于是：

- Prominence II 里 sodium 声明的 `breaks: { supplementaries: "<=1.20-2.7.32" }`
  命中了实际装的 `1.20-3.1.43`（更新），整包被判 BLOCKED，而游戏跑得好好的。
- 所有 `>=1.20-3.0` 这类下界要求同样失效。

但后缀不都是版本段：`flywheel 1.0.5+1.20.1.build.264` 要满足 `>=1.0.5-264`，
这里的 `-264` 是构建号，按版本段比较反而会把 `1.0.5` 判成小于 `1.0.5-264`。

## Decision

按「段」判断，不按分隔符一刀切：

- `+` 之后一律是 build metadata，丢弃（semver 规定不参与优先级）。
- `-` 之后的每一段，**带点的**（`3.1.43`、`47.3.22`、`3.0`）并进主版本：
  `1.20-3.1.43 → [1,20,3,1,43]`。
- `-` 之后**末尾孤零零一个纯数字**（`1.0.5-264`）按构建号处理，丢弃。
- 遇到非数字标签（`beta` / `snapshot` / `rc`）立即停止，后面的段不再参与：
  `1.0.0-beta.1 → [1,0,0]`、`26.4-snapshot-1 → [26,4]`。
- 整串都是标签（`not-a-version`）仍返回 `null` → `unknown`，不猜。

## Consequences

**Positive**

- `1.20-x.y.z` / `1.20.1-<forge>` 这类版本能正确参与区间比较，
  `DECLARED_INCOMPATIBLE` 不再把「比声明更新」误判成命中。
- 构建号不会反过来制造假 blocker（`>=1.0.5-264` 仍然接受 `1.0.5+…`）。

**Negative**

- 单段后缀有歧义：`1.20-3` 会被读成 `1.20`。这类写法在生态里没有实际样本，
  真遇到时按构建号处理更安全（不制造 blocker）。
- 预发布标签仍然没有排序语义（`1.0.0-beta.2` 与 `1.0.0` 相等）。要精确排序得引入
  完整 semver 实现，与「依赖越少越好」的取舍冲突，暂不做。

## Alternatives

- **引入 semver 库**：能处理预发布排序，但模组圈的版本号大量不合 semver
  （`1.20-3.1.43` 本身就不是），库会直接判非法；且增加依赖。
- **只丢 `+`、保留 `-` 后全部内容**：会把构建号变成版本段，`>=1.0.5-264` 立刻误判，
  `src/core/deps/localDeps.test.ts` 里 flywheel 那条用例会红。

## 验证

- `src/core/semver.test.ts`：
  - `1.20-3.1.43` 对 `<=1.20-2.7.32` → `violated`；`1.20-2.7.10` → `satisfied`
  - `>=1.20-3.0` 对 `1.20-2.7.32` → `violated`
  - `1.20.1-47.3.22` 对 `>=1.20.1-47.2.0` → `satisfied`，Maven 区间不受影响
  - `0.92.12+1.20.1` 对 `=0.92.12` → `satisfied`
  - `1.0.5+1.20.1.build.264` 对 `>=1.0.5-264` → `satisfied`
- `src/core/deps/localDeps.test.ts`：JiJ 多份 flywheel 取最高版本那条保持绿
