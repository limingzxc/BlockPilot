# 0049. 版本比较：MC 段与模组段分开比

- **Status**: Accepted
- **Date**: 2026-11-10
- **Deciders**: @liming
- **Related**: ADR-0048（`-` 之后的内容怎么读，本文取代其比较方式）、issue #20

## Context

ADR-0048 把 `-` 之后的数字段并进同一条扁平数组再比：

```
1.20.1-1.3.2  ->  [1, 20, 1, 1, 3, 2]
1.20-1.2      ->  [1, 20, 1, 2]
                    ↑        ↑
                  MC 段   这里开始错位
```

第 4 位比的是「MC 的 patch 号」与「模组的主版本」——两边 MC 段的位数不同时，
模组段整体错位。Better MC BMC4 里 `chefsdelight` 要求 `farmersdelight [1.20-1.2,)`，
实际装的是 `1.20.1-1.3.2`（模组 1.3.2 ≥ 1.2，语义上完全满足），却被判成
`DEPENDENCY_VERSION_MISMATCH` blocker。

ADR-0048 的用例只覆盖了位数相同的情况（`1.20.1-47.3.22` 对 `>=1.20.1-47.2.0`），
所以没暴露。

## Decision

`parseVersion` 返回两段而不是一条数组：`{ mc, mod }`。

- 两侧**都**带模组段时：先按「代」比 MC（前缀比较，`1.20` 与 `1.20.1` 是同一代），
  代相同再比模组段。
- 只要有一侧没有模组段（`1.21` 对 `1.21.2`、`1.20.1-1.3.2` 对 `>=1.20.1`）：
  退回逐位比较、缺位补 0。这类比较里 `1.21` 就该小于 `1.21.2`，
  前缀相等会让 `<1.21.2` 误判成不满足。

`-` 之后的内容怎么切（预发布标签停、末尾纯数字当构建号、`+` 是 build metadata）
仍按 ADR-0048。

## Consequences

**Positive**

- `1.20-x` 的依赖范围能匹配 `1.20.1-x`（以及反过来），Forge 生态里这种写法很常见。
- MC 代不同时仍由 MC 说了算：`1.19.4-9.9` 不会因为模组版本大就满足 `[1.20-1.0,)`。

**Negative**

- `1.20` 与 `1.20.1` 在「两侧都有模组段」时被判为同一代。对依赖范围是想要的，
  但它不是严格的 semver——`1.20` 严格来说是 `1.20.0`。
- 一侧有模组段、另一侧没有时仍走扁平比较：`1.20.1-1.3.2` 大于 `1.20.1`。
  这两种写法混用在同一个依赖里没有实际样本，先保持「多出来的段更大」的直觉。

## Alternatives

- **把短的一侧补 0 到相同长度再拼**（issue 里的退一步方案）：`1.20-1.2` 补成
  `1.20.0-1.2` 能修好下界，但 `[1.20-1.4,)` 对 `1.20.1-1.3.2` 会因为
  `0 < 1` 判成满足，与期望相反。放弃。
- **只比模组段、忽略 MC**：`1.19.4-9.9` 会满足 `[1.20-1.0,)`，跨版本假通过。放弃。

## 验证

`src/core/semver.test.ts`：

```
satisfiesRange('1.20.1-1.3.2', '[1.20-1.2,)')  => satisfied
satisfiesRange('1.20.1-1.3.2', '[1.20-1.4,)')  => violated
satisfiesRange('1.20-1.3.2',   '[1.20.1-1.2,)') => satisfied
satisfiesRange('1.20-3.1.43',  '<=1.20-2.7.32') => violated   // #14 不回归
satisfiesRange('1.21-1.0',     '[1.20-9.9,)')   => satisfied   // MC 代说了算
satisfiesRange('1.21',         '<1.21.2')       => satisfied   // 无模组段走逐位
```

`src/core/deps/localDeps.test.ts` 里 flywheel 的 `>=1.0.5-264` 仍须为 satisfied。
