# 0009. assets：三千个请求的并发与节流

- **Status**: Accepted
- **Date**: 2026-10-25
- **Deciders**: @liming
- **Depends on**: ADR-0005、ADR-0008

## Context

`assets/indexes/5.json` 的实际规模（1.20.1 实测）：

| 指标 | 数值 |
|---|---|
| key 数 | 3,598 |
| 去重后对象数 | 3,575 |
| 总大小 | 621 MB |
| 最大单文件 | 17.7 MB（音乐） |
| 小于 10 KB 的比例 | 21% |

这不是「下载几个大文件」，是「三千次往返 + 少量大文件」。两种负载的特性完全不同：前者吃延迟和连接复用，后者吃带宽。

## Decision

### 1. 按 hash 去重

index 里不同的逻辑路径可能指向同一个对象（同一份音效被多个 key 引用）。实测 3598 → 3575，虽然只省了 23 个，但去重逻辑本身是必须的——某些版本的 index 重复率更高。

### 2. 并发提到 8

默认下载器是 4，那是给模组文件（几百 KB～几 MB）定的。三千个小文件的瓶颈是请求往返而不是带宽，8 路能把墙钟时间压下来，同时对公益镜像仍算克制。

可用 `--concurrency` 覆盖。

### 3. 进度按 50 个一批报

3598 条 `progress` 事件会把 CLI 刷屏，也会让 MCP 的 `notifications/progress` 变成一个 DoS 源。改成每 50 个报一次，最后一个必报。

**失败仍然逐条报**——用户需要知道具体哪个文件没下成，才能决定重试还是忽略。

### 4. 下载 URL 保持官方形态，镜像靠重写

```ts
url: `https://resources.download.minecraft.net/${prefix}/${hash}`
```

不在这里硬编码 BMCLAPI，而是交给 `bmclapiSource.rewrite()`：

```
resources.download.minecraft.net -> bmclapi2.bangbang93.com/assets
```

好处是同一份任务列表可以在直连和镜像之间切换，不用改代码。

### 5. 没有 assets 也能启动

缺 assets 时游戏会缺声音、可能缺字体，但能进主界面。所以 `assets` 是独立命令而不是 `setup` 的一部分——第一次装原版只下 80 MB 就能验证启动链路，621 MB 的音效可以晚点再补。

## Consequences

**Positive**

- 已下载的对象在重跑时会被 sha1 校验后跳过，中断可以续。
- 任务列表是纯函数产出，可以 dry-run 估算体积和文件数。
- 六个单测覆盖去重、路径规则、URL 规则、错误提示。

**Negative**

- **没有真正的断点续传**：单个 17 MB 的文件传到一半断了，重跑要从头下。
- 3575 个并发请求对公益镜像是压力，出问题时要能一键降并发。
- 只按 hash 去重，没有跨版本共享判断（不同版本的 index 会重复下同一批对象，但因为按 hash 存，实际只会命中缓存）。

## 实测

```
index 里 3598 个 key，去重后 3575 个对象 · 621.3 MB
```
